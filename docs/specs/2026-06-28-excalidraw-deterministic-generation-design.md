# Design: Rebuild `excalidraw-generation` as a deterministic, expressive diagram compiler

- **Date:** 2026-06-28
- **Status:** Proposed (brainstorming) — pending user review → implementation plan
- **Scope:** Skill repository (standalone, shareable — stdlib only). Reference/test corpus: ~103 blog `.excalidraw` files (this repo, `articles/**/sources/`) + ~40 talk `.excalidraw` files (talk source folders).

## Context

The current skill (created 2026-06-26 to hand a diagram-generation method to a colleague) is a low-level
element toolkit: `rect / diamond / ellipse / text / arrow / line` flow through `base_element()`, then
`write_excalidraw()` assembles + validates. The author places **every coordinate by hand**.

Two defects were found when checking it against the real diagrams it was meant to reproduce:

1. **Not deterministic.** `id`, `seed`, `versionNonce` use `random.randrange`; `updated = time.time()`;
   `random` is never seeded. So the *same script run twice produces a different file* — and because
   `seed` drives Excalidraw's "rough" jitter, the output even *looks* slightly different each run.
2. **Under-expressive.** It emits only **free-standing text** and **free-floating arrows**. The real
   corpus overwhelmingly uses **bound text** (`containerId` ↔ `boundElements`; 50/103 files) and
   **glued arrows** (`startBinding`/`endBinding`; 36/103) — the toolkit can produce *neither*.

**Provenance of the existing corpus (verified by scan).** The diagrams predate the toolkit and were
generated by Claude two different ways:

- A **clean deterministic generator** for *structured* diagrams — 5-key `appState`, semantic ids
  (`m3y-p1-t`), **sequential seeds** (`100, 101, …`), bound text, glued arrows.
- **Direct freehand JSON emission** for *illustrative* diagrams — a full 92-key `appState` copied
  wholesale, **random** seeds, arbitrary ids, no grouping. This is exactly the *"LLM emits JSON field
  by field"* anti-pattern the skill's own README warns against, and it is **non-deterministic**.

**Element vocabulary** across all ~143 files: only six types — `text, rectangle, arrow, line, ellipse,
diamond`. No `image / frame / freedraw`. Even the richest illustrations (stick figures, cloud, die,
lock/eye/peak icons) are **pure primitive compositions** (lines + ellipses), never `freedraw`. Median
21 elements/file (min 7, max 60).

## Goal

Rebuild the skill so Claude can generate **any** of these diagrams **deterministically** — same input
⇒ same picture — covering everything Claude currently produces freehand, so there is **never a reason
to drop back to raw JSON** (which is the only way determinism gets lost).

## Goals

- **Visual determinism.** Same spec ⇒ same rendered image. File internals (`id`, `versionNonce`,
  `updated`) may differ; every *visually load-bearing* field is a pure function of the input.
- **Full expressiveness (= freehand parity).** All 6 primitives + bound text + glued arrows + nesting +
  grouping + multi-point/curved/loop arrows + dashed strokes + hachure fill + the 3 fonts + axes/charts
  + free composition. If Claude can draw it freehand, the skill can emit it.
- **Two styles, one compiler.** *Structured* (bound text, glued arrows, semantic panels, auto-layout)
  and *illustrative* (free primitive composition) are both expressible through one surface.
- **Standalone & shareable.** No dependency on `editorial-workflow`; copy the folder and `import` —
  Python standard library only.

## Non-Goals

- **Auto-designing metaphors/icons.** The skill is a deterministic **renderer**, not an **illustrator**:
  *what* to draw (the composition) is authored; the skill only guarantees it renders deterministically
  and validly. "Draw me a tool symbol" is never reproducible; "render *this* composition" always is.
- **Inventing chart data.** Curve/bar/histogram values come from the input, or from a deterministic
  function-eval helper — never fabricated.
- **A generic graph auto-layout engine.** The two hardest corpus archetypes (curves = real data points;
  content-sized hierarchies) defeat it; explicit positions cover them and everything else. *Considered,
  rejected* (over-engineering for median-21-element diagrams).
- **Natural language as the determinism boundary.** An LLM turning prose → spec is non-deterministic by
  nature; the guarantee lives at **spec → file**, not request → file.
- **A prebuilt icon library.** v1 = explicit primitive composition + `group()`. A curated icon-kit is a
  possible later add-on (YAGNI now).

## Design

### 1. Determinism model — field taxonomy

| Class | Fields | Rule |
| --- | --- | --- |
| **Load-bearing** (pure function of input) | geometry (`x, y, width, height, points`), colors, `strokeStyle/strokeWidth`, `fillStyle`, `fontFamily/fontSize`, z-order (`index` + array order), **`seed`** | derived deterministically from the input |
| **Cosmetic** (free to vary, invisible) | `id`, `versionNonce`, `updated` | — |

`seed` is the trap: it *looks* like plumbing but drives the roughness jitter, so it **must** be
content-derived. Rules:

- `seed = stable_seed(diagram_id, element_id)` via **`hashlib`** — **not** Python's builtin `hash()`,
  which is `PYTHONHASHSEED`-salted per process and would silently destroy determinism:
  ```python
  import hashlib
  def stable_seed(diagram_id, element_id, salt=""):
      h = hashlib.sha1(f"{diagram_id}/{element_id}/{salt}".encode()).hexdigest()
      return int(h, 16) % (2**31 - 1) + 1     # Excalidraw seed ∈ [1, 2^31)
  ```
- `id`: **semantic, author-assigned** in the spec (`rc-header`, `icon-lock-shackle`) — stable, readable,
  content-addressed. (This is also what the clean corpus diagrams already do.)
- `versionNonce = stable_seed(diagram_id, element_id, salt="nonce")`.
- `updated`: a **fixed constant** (or a spec-provided value), never `time.time()`.
- `index`: sequential fractional-indexing keys `a1 … aN` in document order.
- `appState`: always the clean **5-key** set.
- `diagram_id` defaults to the output filename stem. Salting seeds by it keeps identical element ids in
  *different* diagrams independent — and lets DE/EN variants of the *same* diagram share a `diagram_id`
  so they render identically modulo text (desirable parity).

**Boundary:** `spec → file` is a pure function at the visual level. Authoring (Claude: intent → spec) is
explicitly outside the guarantee.

### 2. Architecture — two layers

- **Layer 1 — Core compiler** (deterministic, expressive). The single chokepoint: a declarative
  element/relation API → valid `.excalidraw`. Owns required-field population, **reciprocal bindings**
  (bound text + glued arrows), z-order, the determinism rules above, and validation. It is the rebuilt,
  de-randomized, binding-capable successor of today's `excalidraw_toolkit.py`.
- **Layer 2 — Helpers** (optional sugar over the core; they emit core elements and never bypass it).
  Three families:
  - **Layout:** `flow_row`, `grid`, `columns` / `stack`, `timeline`.
  - **Charts:** `axes`, `bars`, `curve` (deterministic function eval), `histogram`.
  - **Composition:** `group`; *(later, optional)* a curated icon-kit.

Per diagram the author picks the layer: illustrations → core primitives + `group`; structured diagrams →
bound text + glued arrows + layout helpers; charts → chart helpers.

### 3. Input surface — Python builder API (the "spec")

The spec is a **Python builder API**, not a YAML/JSON DSL:

- The author is an agent (Claude) that writes Python comfortably; a YAML layer adds a translation step
  and **cannot express function-eval** (`curve(lambda t: 100*e**(-t/S))`) or programmatic generation
  (50 curve points, N grid cells) without reinventing a DSL.
- The Python script *is* the deterministic input: same script ⇒ same visual output (the compiler is
  pure). Content-hashed seeds make it robust to later reordering/editing.
- Minimal change: **evolve the existing toolkit** into the core compiler rather than inventing a
  parallel format. (A declarative YAML front-end remains a possible future convenience; not built now.)

### 4. Core capability list (derived from the corpus — the "must support")

| Capability | Corpus example |
| --- | --- |
| **Bound text** (label inside a shape, moves with it) | `three-layers`, `delegation-layers` |
| **Glued arrows** (`focus`/`gap`, reconnect on move) | `workflow-bug-investigation` |
| **Multiple texts per box** (bold title + gray subtitle + caption) | `delegation-layers`, failure-mode cards |
| **Nesting** (box-in-box, multi-level / concentric) | `consistency-metrics`, `triade_tabelle`, `berater_buero` |
| **Grouping** (an icon/figure lives as one unit) | all illustrations — *added value: originals weren't grouped* |
| **Multi-point / curved / loop arrows** | `ebbinghaus` curve, `triade` loop |
| **Dashed + labeled connectors** | `consistency-metrics` ("SDD-Restrukturierung"), `berater` bridge |
| **Ellipse compositions** (cloud, speech bubble, die pips) | `berater_buero`, `wuerfel_verteilung` |
| **Axes + ticks + reference lines** | `ebbinghaus`, `locomo-benchmark` |
| **Dashed strokes / hachure fill / 3 fonts** (hand=1 default, code=3, normal=5) | corpus-wide |
| **Unicode/emoji in text** (✅) | `consistency-metrics` |

### 5. API sketch (illustrative signatures — final names settled in the plan)

```python
# Primitives — every element takes an explicit semantic id
rect(id, x, y, w, h, *, fill="transparent", stroke="#1e1e1e", dashed=False, rounded=True)
ellipse(id, x, y, w, h, ...); diamond(...); line(id, points, ...); text(id, x, y, w, h, content, font="hand")
arrow(id, points, *, end_head="arrow", dashed=False)

# Bound text (reciprocal containerId <-> boundElements wired automatically)
rect(..., label="Input", label_font="code")          # convenience
label(text_id, container, content, ...)               # explicit

# Glued arrow: computes endpoint geometry + start/endBinding(focus, gap) + optional mid-label
connect(id, src, dst, *, label=None, dashed=False, end_head="arrow")

group(id, elements)                                   # icon/figure as a unit

# Layout helpers (emit core elements)
flow_row(items, *, y, gap); grid(cells, cols, ...); columns(col_specs, ...); timeline(points, ...)

# Chart helpers (data is input, never invented)
axes(x_range, y_range, ticks=...); bars(data, ...); curve(fn, t0, t1, n=60, ...); histogram(data, ...)

# Assembly — diagram_id (default = path stem) drives seed hashing
write_excalidraw(path, elements, *, diagram_id=None)
```

### 6. Validation & determinism invariants

Extend today's validator (required fields, index-key legality, 5-key `appState`, top-level key order)
with:

- **Binding integrity:** every `containerId` has a matching `boundElements` entry and vice-versa; every
  binding `elementId` resolves to an existing element.
- **No nondeterminism:** no `time.time()`-derived `updated`; seeds reproducible.
- **Determinism self-test:** compile a scene **twice**, assert identical load-bearing fields.

### 7. Worked decompositions (proof of coverage — both styles)

- **Structured —** `three-layers`: `columns([...])` + `label(...)` for each panel + `connect(...)` for
  the inter-layer arrows.
- **Illustrative —** `berater_buero`: core primitives + `group("office", [box, llm_circle, bubble])` +
  `connect("bridge", office, tools, label="braucht")`.
- **Chart —** `ebbinghaus`: `axes(x_range=(0,30), y_range=(0,100))` +
  `curve("forget", lambda t: 100*e**(-t/S), 0, 30, n=60)` + dashed drop-lines.

### 8. PNG export

Unchanged: a manual GUI export from a real Excalidraw client (zero deps, pixel-exact) — documented in
`png-export.md`. No CLI rasterizer is bundled (faithful rendering needs Excalidraw's own engine).

### 9. Scope / phasing

- **v1:** core compiler (de-randomized + bindings + grouping + multi-point arrows + dashed/hachure/fonts)
  + layout helpers + chart helpers + explicit icon composition via `group`.
- **Later/optional:** curated icon-kit; YAML front-end.
- File deltas in the skill: `excalidraw_toolkit.py` rewritten into the core compiler; `example_flow.py`
  replaced by per-style worked examples (structured / illustrative / chart); `format-reference.md`
  extended with the binding fields; `SKILL.md` rewritten around the two-layer model + determinism rules.

### 10. Why this shape (the `editorial-workflow` parallel)

The original ask was to mirror how `editorial-workflow` achieves determinism. It does so via **input
normalization** (the 12-field briefing), a **tooling-vs-judgment split** (`wordcount.py` does everything
numeric/structural; the model only judges substance/style), and **persistent artifacts + a validation
gate**. This design transplants the *pattern*, not the *weight*: the **spec** is the normalized input
artifact, the **core compiler** is the deterministic tooling, the **validator** is the gate — but a
*light* pipeline (one compile + validate), not a 22-phase workflow. The skill stays standalone;
`editorial-workflow` may later delegate to it (as it already delegates `image-generation`), but that
integration is out of scope here.

## Testing / Verification

- Validator unit tests: binding integrity, 5-key `appState`, index keys, no-nondeterminism.
- **Determinism golden tests:** N representative scenes compiled twice → identical load-bearing fields.
- **Reproducibility benchmark (the litmus test):** re-express a sampled subset of the ~40 talk + blog
  files through the API, open in Excalidraw, confirm visual match — i.e. confirm there is no diagram in
  the corpus that still needs raw-JSON.
- TDD throughout (the implementation plan drives this).

## Risks / open questions

- **Glued-arrow geometry.** Computing endpoint `points` + `focus`/`gap` so Excalidraw re-routes
  correctly. The corpus uses `focus:0, gap:1` with explicit points spanning shape edges — reverse-engineer
  the exact edge-intersection formula during implementation.
- **Curve fidelity.** Point count and `roundness:{type:2}` smoothing for natural curves; axis scaling
  (explicit ranges by default, no surprise auto-scaling).
- **Icon ergonomics without a kit.** Explicit composition can be verbose; mitigate with `group()` +
  relative coordinates; revisit an icon-kit only if real usage shows repetition.
- **DE/EN parity.** Whether DE/EN variants share `diagram_id` (→ identical layout/jitter modulo text).
  Default: share the base id.

## Open implementation details (decided during implementation, no further input needed)

- Module layout (single file vs core + helpers split).
- Precise edge-intersection math for `connect`.
- Helper parameter defaults (gaps, paddings) calibrated against corpus medians.
